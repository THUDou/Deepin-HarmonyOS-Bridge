# ADR-0002：两档能力模型（Core / Pro）

- 状态：Accepted
- 日期：2026-10-27

## 背景

零售 HarmonyOS NEXT 对三方应用的系统能力有明确限制：可以调用公开的设备发现/PIN 绑定、文件选择/分享、剪贴板（前台）、通知发布；但没有公开证据表明三方应用可以整机录屏或向其他应用注入输入。KaihongOS/OpenHarmony 系统应用则可以通过 ACL/系统签名获得这些能力。

如果只做一档：

- 只做零售：产品价值被压缩成"文件传输 + 副屏"，但可上架、可验证；
- 只做系统：能力完整，但依赖厂商合作/烧机，短期无法触达用户。

## 决策

采用 **Core / Pro 两档**，共用同一套 DHB 协议与核心库：

| | Core | Pro |
|---|---|---|
| 目标设备 | 零售 HarmonyOS NEXT + Deepin/UOS | KaihongOS/OpenHarmony 系统签名 |
| 传输 | TCP/TLS（dsoftbus 仅发现/绑定） | Klink/dsoftbus 原生 |
| 能力 | 文件、剪贴板、通知、Linux→鸿蒙副屏 | + 鸿蒙→Linux 镜像回控、hmdfs、分布式硬件 |
| 分发 | 应用市场 HAP + deb | 系统镜像/预装/企业交付 |

代码上用 `caps` 协商与 `ITransport` 抽象隔离，不复制业务逻辑。

## 后果

**正面**

- 今天就能交付可用产品，同时保留系统级护城河。
- 对外预期清晰，减少"为什么不能镜像手机"的沟通成本。
- 同一协议/测试覆盖两档，降低长期维护成本。

**负面**

- 文档、测试矩阵、打包都要 ×2。
- Core 的 TLS/应用层通道需要额外安全投入。
- Pro 的商业化依赖 KaihongOS/整机厂商。

## 复审条件

- 零售 NEXT 开放整机录屏/输入注入的公开 API；
- KaihongOS 成为主流桌面发行版，Pro 可直接覆盖大多数用户；
- 两档代码出现不可接受的重复。
