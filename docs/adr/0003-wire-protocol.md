# ADR-0003：自定义二进制帧协议，而不是 JSON/protobuf

- 状态：Accepted
- 日期：2026-10-27

## 背景

DHB 需要同时承载：

- 低频控制（HELLO、认证、文件元数据、剪贴板）；
- 高频大块数据（256 KiB 文件块、未来的视频帧、输入事件）；
- 两种语言实现（C++17 / ArkTS），未来可能加 Rust/Go；
- 可调试、可版本化、可模糊测试。

候选：JSON、Protocol Buffers、FlatBuffers、自定义二进制。

## 决策

采用 **自定义二进制帧 + 类型化 payload**：

- 20 字节头：magic/version/type/flags/stream/length/CRC-32C；
- 控制消息用小端字段 + 长度前缀字符串；
- 文件块/视频帧直接放 payload；
- 版本号 + 能力位协商；未知类型忽略。

## 理由

- JSON 对文件块/视频不合适（编码开销、二进制支持差），且 C++ 需要引入 JSON 库。
- protobuf 需要代码生成与两端工具链，MVP 阶段增加构建复杂度；ArkTS 支持也一般。
- 自定义格式足够简单（~300 行 C++），可用单元测试覆盖；CRC 提供早期损坏检测。
- 帧头固定，便于 Wireshark 解析器/抓包工具后续开发。

## 后果

**正面**

- 零依赖、跨语言、紧凑；文件/屏幕共用一条会话。
- 协议文档即规范，测试向量明确。
- 易于加自定义流（屏幕/输入/音频）。

**负面**

- 两端编解码需要手工同步；靠 `docs/03-protocol.md` + 测试约束。
- 无 schema/IDL，字段演进要谨慎（v1 要求无尾随字节）。
- 调试不如 JSON 直观；需要 `dhb dump` 工具（M2）。

## 备选方案

- **JSON**：仅用于控制面，文件面另开二进制。复杂度更高，放弃。
- **protobuf**：等协议稳定、需要多语言 SDK 时再评估；可作为 v2 的兼容层。
- **直接复用 dsoftbus 消息**：受限于系统 API，且无法覆盖 TCP 路径。

## 复审条件

- 协议字段超过 ~40 种，手工维护成本过高；
- 需要正式 SDK/多语言绑定；
- 性能分析显示 CRC/拷贝成为瓶颈（届时评估零拷贝/头部校验）。
