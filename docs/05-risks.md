## 重点风险详解

### R1 零售 NEXT 权限

这是**产品定位风险**，不是纯技术风险。公开 API 声明显示 `distributedDeviceManager` 的发现/PIN 绑定可用，但没有公开的任意字节 dsoftbus 通道；整机录屏与跨应用输入注入按系统能力处理。应对：

- Core 档把"鸿蒙作为副屏"作为主卖点，而不是"手机镜像到 PC"。
- Pro 档与 KaihongOS 厂商合作，走系统签名/ACL；在协议与代码上与 Core 共用，避免两套产品。
- 对外文档明确能力矩阵，减少预期错位。

### R2 Klink 版本

Klink 官方说明兼容"鸿蒙软总线 4.x 协议"，KaihongOS 5.x 基于 OpenHarmony 5.x。dsoftbus 的发现/认证/session 在 4→5 之间可能有变化。应对：

- M0 第一周就用真机/虚拟机跑 `klink_probe`，记录发现、PIN、session、字节传输四步。
- 失败时先看是"发现/认证"还是"session 协议"；前者可换手动配对，后者需要 rebase。
- rebase 工作量估计 2–4 人周（Klink 已做 Linux 适配，主要是 dsoftbus 版本 diff + HiChain 接口）。

### R8 安全

当前 v0.1 的 TCP 是**明文**，仅用于本机/可信局域网开发；这是已知缺口，不是可发布状态。M1 必须：

- TLS 1.3 + 证书 pinning（或 PAKE）。
- 文件接收加 `O_NOFOLLOW`、大小上限、磁盘配额。
- 帧解析模糊测试（libFuzzer/AFL）。
- 第三方安全审计（至少一次）。

### R9 范围

DHB 很容易被拉成"什么都要"：游戏串流、远程桌面、云盘、账号体系、Android 兼容。**每加一个功能，问三个问题**：

1. 它是否强化"信创桌面 ↔ 鸿蒙"的差异化？
2. 它是否能在 2 周内做出可演示切片？
3. 它是否引入新的合规/安全面？

三个都是"否"就拒绝。
